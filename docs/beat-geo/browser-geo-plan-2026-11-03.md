# BeatGEO：域名、问题库与真实浏览器监测完善清单

日期：2026-11-03。本文是本轮范围决策与待办，不代表功能已经实现或真实验收通过。本轮补齐 SEO 数据展示与 SEO / GEO 导航分组，详见 [SEO / GEO 界面方案](seo-geo-experience-2026-11-03.md)。Google 客户端配置、后续 GEO 功能和真实验收安排在下一次工作中（2026-11-04），不是自动执行或定时通知。

## 1. 产品主线与明确边界

服务任意网站的站主，不依赖网站使用哪种 CMS。

**输入域名 → 理解业务并让用户确认 → 建立问题库 → BeatBrowser 在用户已登录的浏览器中向 AI 平台提问 → 留存回答与引用 → 发现缺口 → 用户实施改进 → 用相同问题复测。**

- BeatGEO 管理网站、问题、任务、证据、建议与复测；沿用现有数据库、队列、工作台和 MCP。
- BeatBrowser 复用用户同机浏览器与登录状态。不是云浏览器，不承诺独立账号隔离、离线采集或无人值守通过验证码。
- BeatAPI 用于网站研究、问题建议、证据分析、草稿与已有 SEO 数据补充。模型生成建议不能充当真实浏览器监测结果。
- GSC/GA 是可跳过的辅助连接。未授权也能手动确认业务、编辑问题并进行浏览器监测。
- SEO 仅使用已有端点解决具体任务。没有现成端点的能力不为了追平竞品而扩建；已有端点也不要求全部显示在主界面。
- 本轮排除 WordPress、Shopify、其他 CMS 发布连接器、页面自动写回、本地商家/Maps/商家问答，以及新增地区和设备筛选。不是通用 SEO 排名工具。
- 不新增 DataForSEO 采购或 AI 提及数据库，不把 API 模拟、第三方样本库、真实浏览器回答混成一种数据。

## 2. 从 Conqueror 吸收什么

| 借鉴点 | 在 BeatGEO 中的落点 | 不引入的内容 |
| --- | --- | --- |
| 连接后快速看到下一步 | 完成域名与问题确认后，优先完成少量真实基线，给出有依据的建议 | 强制 GSC、完整 SEO 报表或 CMS 设置 |
| 使用已有证据生成候选 | 网站内容为主；可选 GSC 查询、已有 SEO 结果辅助 | 把 Google 搜索量当 AI 提问量 |
| 保存研究上下文 | 问题有来源、类型、状态和版本，后续工作复用同一问题库 | 另建一套关键词/品牌数据库 |
| 从结果进入行动 | 从某条回答或引用创建有基线的优化任务 | 一键宣称提升排名、自动发布 |
| 原文和修改可审阅 | 显示证据、生成理由、草稿版本，用户自行实施 | 站点密码、CMS 写权限与发布维护 |
| Agent 与界面互通 | 扩展现有 MCP 和本地工作流，保持同一记录与权限 | 新建独立远程 MCP 产品、第二套账户 |
| 持续检查而非一次性报告 | 本机条件允许时执行复测，失败和缺失单独展示 | 电脑关闭后继续采集的承诺 |

## 4. 按优先级实施的功能清单

状态统一为“计划/待核验”。开发前逐项复查已有行为；能复用的补体验和验收，不重复实现。

### P0：让一个网站完成一轮真实监测

**G01 — 统一首次使用流程**

- 输入域名后显示识别出的业务、目标用户、核心用途、品牌别名和建议竞品；用户可以修改。
- 只确认实际需要的信息，不能仅凭域名字符串推断业务。
- 用户可以跳过 Google 与 SEO 连接；提供手填入口。
- 验收：一个 API 网站与一个不同业务的网站获得不同业务画像与问题候选；来源不足时明确提示。

**G02 — 问题库成为主工作对象**

- 按品类发现、场景、选型比较、功能、限制、品牌认知等组织候选问题。
- 区分不点名品牌的发现类问题与主动问品牌的问题；后者不能混入自然发现提及率。
- 每条候选记录来源类型、来源页面或查询、建议理由；AI 生成标为建议，不能标为真实用户需求量。
- 支持增删改、勾选启用、去重与同义候选提示；自动生成不得覆盖用户手动修改。
- 更新保留来源与版本；题目或品牌定义改变后提示历史结果不再直接可比。
- 验收：只运行用户确认启用的精确问题，重复导入不重复创建，编辑后能解释比较范围的变化。

**G03 — 运行前就绪检查与小批量首跑**

- 区分 BeatBrowser 未连接、版本不匹配、浏览器已连但 AI 平台未登录、执行器忙、worker 离线。
- 让用户知道本轮要问哪些问题、哪些已支持平台、多少次采集；先用少量问题获得基线。
- 不把研究关键词、SEO 分数或额外品牌提示偷偷加入实际提交的问题。
- 本轮先验收已有平台适配器，不为对齐竞品而新增平台承诺。
- 验收：页面提交文本与已确认问题一致；没有 Google OAuth 也能完成首跑。

**G04 — 可理解且可恢复的任务状态**

- 显示排队、运行、完成、失败、需要人工处理、取消等真实状态及逐项进度。
- 保留已成功部分；重试只针对明确选中的失败或未完成项，不重新提交整批成功问题。
- 不能把队列完成当作采集成功，不能把空回答或未登录当作零提及。
- 验收：中途断连、浏览器忙和重复点击均不会制造重复成功记录；人工暂停不会被自动绕过。

**G05 — 回答与引用证据详情**

- 展示问题、平台、时间、原始回答、品牌匹配片段、竞品片段和来源链接。
- 明确“正文提及”与“引用本站”；网址规范化与域名归属可解释。
- 核验当前未展开来源面板的局限；能支持的平台补完整来源读取，不能支持则保留覆盖说明。
- 平台页面未暴露的模型信息保持未知，不伪造精确版本。
- 验收：每个提及和引用结论都能回到实际回答证据；失败样本不进入有效回答分母。

**G06 — 首次结果与下一步**

- 首屏回答：哪些问题里出现了我、哪些只出现竞品、哪些回答引用本站或第三方，以及本轮覆盖多少。
- 只给少量优先建议，写清证据和具体承接页；证据不足可以没有建议。
- 建议类型聚焦回答用户问题、补充可核实事实、完善 FAQ/说明/比较内容，而非承诺排名提升。
- 验收：从建议能进入相关原始回答并创建现有优化任务，不再让用户重新填写同一组问题。

### P1：辅助资料、行动与复测形成持续流程

**G07 — 完成 GSC/GA 客户端与真实连接验收**

- 配置开发用 Google OAuth 客户端、必要 API 和回调；用户亲自同意授权。
- 分别验证属性选择、读取、刷新、拒绝授权、权限失效、空数据及本地断开。
- GSC/GA 可分别连接与跳过。授权不是全部属性都已绑定，浏览器登录也不是 API 授权。
- GA 来源会话仅作为辅助流量观察，不与 AI 回答样本拼成已证明的转化链。
- 验收：真实站点产生可读结果，失败不覆盖最后一次成功数据；秘密不出现在前端和导出中。

**G08 — GSC 搜索词转问题候选**

- 用户选择与业务相关的查询，生成自然语言问题候选并保留原查询；逐条确认后进入同一问题库。
- 补 `query × page` 关联，帮助识别现有内容对应的问题；不是建设全面排名追踪产品。
- 不因为 GSC 有某个查询就自动把它转为监测问题，也不承诺返回所有搜索词。
- 验收：候选能回溯到查询与页面，已有手工问题不被覆盖，无关查询可排除。

**G09 — 用现有 BeatAPI SEO 端点补研究**

- 围绕已选主题、竞品或被引页面按需调用已有关键词、域名、Top Pages、外链等端点。
- 批量按现有契约拆分，去重、缓存并显示范围与费用；不为复刻“700 词一调”新增上游能力。
- 输出是问题候选、研究依据或内容参考，关键词量与难度不进入浏览器提及率的计算。
- 不新增本地商家、地区/设备筛选、实时 SERP 专项或第三方 AI 提及库。
- 验收：没有对应端点的功能被省略；部分失败保留其余结果，过期缓存有时间标识。

**G10 — 问题、页面和行动关联**

- 一个问题可关联已有页面或待创建内容；推荐页面需依据站点内容、GSC 关联或用户选择。
- 缺少证据时标记“建议页面/未确认”，不根据标题相似就断言是最佳页面。
- 复用现有草稿、编辑、审核与 Markdown 导出；用户自行在网站上实施。
- 保存实施说明、页面 URL 和时间；“草稿已审核”与“网站已修改”必须是不同状态。
- 验收：形成可执行内容建议，无 CMS 登录、自动发布或网站写权限。

**G11 — 可比较的复测与历史**

- 对同一版本的问题、品牌定义和相同采集配置复测，显示匹配样本数、缺失数和失败数。
- 保留回答历史、来源变动、行动前基线与实施记录，允许从变化跳回原文。
- 网页平台、账号和上下文会变化；仅陈述所观察到的差异，不承诺完全可重复或证明因果。
- GSC/GA 若用于辅助比较，需保留日期与历史快照，不把一次最新快照包装为趋势。
- 验收：问题改动、平台不同或缺少结果不会被误算为提升/下降；小样本不生成确定性结论。

**G12 — 本地持续运行与用户掌控**

- 复用已有调度，清楚显示是否启用、下次运行、依赖哪些本机组件。
- 电脑睡眠、浏览器离线或需登录时显示原因；恢复后不无上限补跑。
- 调度开启需要用户操作；不把手动首跑等同于启用持续监测。
- 验收：暂停阻止后续提交；正在运行的任务如何结束有清楚说明；离线不显示正常完成。

### P2：主流程通过真实验收后再增强

**G13 — 统一 Agent 与工作台入口**：审查现有 MCP 已覆盖的操作，只补必要的辅助连接状态、来源候选和任务读取；同一操作共享权限、幂等和记录。输出“分析网站/补问题/跑基线/复测行动”的工作流文档，避免另建服务。

**G14 — 导出与复盘**：导出指定运行的问题、回答、来源、失败覆盖和建议，注明日期与样本口径；不导出授权令牌。周报只汇总已发生的有效观察，不把单次抖动包装成趋势。

**G15 — 业务相关性与建议质量评估**：用不同类型网站检查问题是否贴合业务、是否诱导品牌出现、建议是否有事实依据、用户是否能执行。以首轮有效采集、问题采纳、行动实施和复测完成作为产品验证，不以生成条数代替价值。

## 5. 下一次工作的执行顺序与停止条件

1. 复核固定主目录的运行环境与旧配置/数据的安全恢复，不能直接覆盖或运行未经确认的数据迁移。
2. 配置 Google 客户端并验收 G07；用户登录与授权需本人完成。此项不阻塞独立的 BeatBrowser 基线验收。
3. 用一个真实网站跑 G01–G06，记录现有功能的通过项与缺陷，不先重写已有模块。
4. 按实际缺口实施 G02/G05，以及 G08 的查询到问题与页面关联。
5. 完成一个有依据的 G10 行动，再验证 G11 复测。没有实际修改时比较两次采样，不伪造实施记录。
6. 只在以上主线可用后推进 G09 的辅助研究和 G12–G15 的持续体验。

本轮完成标准：用户能从域名建立可编辑、可追溯的问题库，通过其真实浏览器获得至少一组有效回答及来源，创建并审阅一项有证据的改善建议，并知道如何在自行修改网站后复测。CMS 发布、多地区排名和竞品全部功能不属于完成标准。
